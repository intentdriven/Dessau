# Re-verifying the model-server assumptions against mlx-lm 0.32.0 — 2026-10-03

The pin is moving from `mlx-lm==0.31.3` to `mlx-lm==0.32.0`
(`internal/runtime/mlx-requirements.txt`; `mlxLMVersion` in
`internal/runtime/provision.go`; `samplingFlagsVerifiedAgainst` in
`internal/runtime/launcher.go`). This note re-reads the 0.32.0 source for every
assumption Dessau holds about the model server, and says for each whether it
HOLDS or has CHANGED. It is the evidence
`TestSamplingFlagsWereVerifiedAgainstThePinnedServer` asks for before the
constant may move. The 0.31.3 evidence is in
`2026-09-06-mlx-lm-sampling-launch-flags.md` and
`2026-09-20-mlx-lm-0.31.3-debug-logging.md`, and in the 2026-10-03 lines of
`.abcd/work/DECISIONS.md` on the served window, `model_file`, the refused
request fields and the socket launcher.

Method: both wheels were unpacked outside the repository (`mlx_lm/_version.py`
reports `0.31.3` and `0.32.0`; `mlx_lm/server.py` is 1,904 and 1,945 lines).
The 0.31.3 copy matches the line numbers the earlier notes cite, so the
comparison is against the same artefact. Every claim below is read from
`mlx_lm/server.py` and the modules it imports, and checked with a `diff` of
the two trees. Where a finding turns on `transformers`, that package was read
at 5.14.1, the version the lock file pins. Nothing was run: there is no Apple
Silicon machine and no `mlx` here, so the one finding with a behavioural
consequence (check 2) is a static trace, and it wants a hand check on a Mac
before the pin lands. Line numbers are 0.32.0 unless a version is named.

## 1. Sampling launch flags: HOLDS

Every flag `samplingArgs` passes is still in the argument parser of
`main()`, with the same name, type and default. The `diff` of the two
`server.py` files has no hunk in that region.

| Flag | 0.32.0 | Quoted |
| --- | --- | --- |
| `--temp` | 1840–1844 | `type=float,` `default=0.0,` |
| `--top-p` | 1846–1850 | `type=float,` `default=1.0,` |
| `--top-k` | 1852–1856 | `type=int,` `default=0,` |
| `--min-p` | 1858–1862 | `type=float,` `default=0.0,` |
| `--max-tokens` | 1864–1868 | `type=int,` `default=512,` |

The meaning is the same, because the request side is the same. `do_POST` reads
each as `self.body.get("temperature", self.response_generator.cli_args.temp)`
and its three siblings (1172–1177), and `max_tokens` as described under check
2. The ranges are the same: `validate_model_parameters` (1227–1245) reads

```
self._validate("max_tokens", int, min_val=0)                          # 1230
self._validate("temperature", (float, int), min_val=0)                # 1231
self._validate("top_p", (float, int), min_val=0, max_val=1)           # 1232
self._validate("top_k", int, min_val=0)                               # 1233
self._validate("min_p", (float, int), min_val=0, max_val=1)           # 1234
```

and it still runs on the effective value, so the failure mode the 0.31.3 note
records (an out-of-range launch flag surfacing per request, uncaught) is
unchanged.

The sampler's own limits are unchanged in substance. `apply_top_k` in
`mlx_lm/sample_utils.py` still raises unless `0 < top_k < vocab_size` (line
150: `if not isinstance(top_k, int) or not (0 < top_k < vocab_size):`; only the
message text changed, from `(0, {vocab_size}]` to `(0, {vocab_size})`).
`apply_min_p` still raises outside `0 <= min_p <= 1.0` (line 184).
`make_sampler` still returns the argmax sampler at temperature 0 (line 49, now
the named `greedy_sampler`) and still applies top-p only when
`0 < top_p < 1.0` (line 55). `apply_top_p` was rewritten (a cumulative-mass
comparison instead of an inverse permutation), with the same contract.
`MaxTopK` at 1024 therefore remains far below any vocabulary and needs no
change.

**No new sampling flag.** The three new flags are about the KV cache, not
sampling: `--kv-bits` (1905), `--kv-group-size` (1913) and
`--quantized-kv-start` (1919). `--kv-bits` matters in one way: when it is set,
`_is_batchable` returns false (`and self.cli_args.kv_bits is None`, 649–653), so
every request is served one at a time. Dessau does not pass it. No new
repetition, penalty or logit flag exists either; those are still read from the
request body only.

One request default moved, with no effect on Dessau. `xtc_threshold` now
defaults to `0.1` (line 1185: `self.body.get("xtc_threshold", 0.1)`; it was
`0.0`), and `make_sampler`'s own default moved to match. XTC is applied only
when `xtc_probability > 0.0` (`sample_utils.py` 59), and `xtc_probability`
still defaults to `0.0` and has no launch flag, so a request that names
neither is unaffected. The seed is as before: `--seed` is not a flag, and a
request that carries `seed` leaves the batched path (`args.seed is None` in
`_is_batchable`).

The one exception to "the ranges are unchanged" is not in the range but in
what happens after it: see check 2, `max_tokens` of zero.

## 2. Served window and max tokens: CHANGED

### What holds

- **How a request's budget is read.** Unchanged, at 1167–1171:

  ```
  self.max_tokens = self.body.get("max_completion_tokens", None)
  if self.max_tokens is None:
      self.max_tokens = self.body.get(
          "max_tokens", self.response_generator.cli_args.max_tokens
  ```

  `max_completion_tokens` wins when present and not `null`; otherwise
  `max_tokens`; otherwise the launch flag. This is what
  `requestedMaxTokens` in the gateway mirrors, and what the omitted-budget
  fix of 2026-10-03 rests on.
- **The launch default is still 512 and still the answer to an omitted
  budget** (1864–1868, above). The 2026-10-03 line on the cut-off at 512
  tokens stays true of 0.32.0, and so does its remedy: `launchSampling`
  passing `--max-tokens` equal to the served window.
- **No window is enforced by the server.** `max_kv_size` appears nowhere in
  `server.py`. The prompt cache is made with `make_prompt_cache(self.model_provider.model)`
  (951), and `BatchGenerator` is built without it (the constructor takes
  `max_kv_size: Optional[int] = None`, `generate.py` 1534). The server does not
  take the prompt off the budget, so the cost the 2026-10-03 line records as
  accepted (one request can grow its cache past the window the memory budget
  charges for) is unchanged.
- **`--decode-concurrency` exists** with the same type and default
  (1876–1880: `type=int,` `default=32,`) and is passed on as
  `completion_batch_size=self.cli_args.decode_concurrency` (line 789).
  `BatchGenerator` still raises it to at least `--prompt-concurrency`:
  `self.completion_batch_size = max(completion_batch_size, prefill_batch_size)`
  (`generate.py` 1544; line 1520 in 0.31.3), with `--prompt-concurrency`
  defaulting to 8, so a decode concurrency below 8 is raised to 8 exactly as
  before.

### What changed: a budget of zero now stops the generation thread

The 0.31.3 note says a budget of `0` "is accepted and yields nothing". That was
true of the single-request path only. 0.32.0 changes both paths, and the batched
one (the path every ordinary request takes) goes from "one token" to "kills the
generation thread".

1. **Validation still accepts zero.** `self._validate("max_tokens", int, min_val=0)`
   (1230). Python's `bool` is an `int`, so `false` is accepted as well; a float
   such as `0.0` is not an `int` and is refused with a `ValueError` in the
   request thread, as before.
2. **The batched path now refuses a non-positive budget, and nothing catches
   it.** `BatchGenerator.insert_segments` (`generate.py`) gained

   ```
   if m <= 0:
       raise ValueError(f"Sequence {uid}'s max_tokens must be > 0.")
   ```

   at 1670–1671. In 0.31.3 there was no such check, and a budget of zero ended
   after one token (`if self._num_tokens[i] >= self.max_tokens[i]:
   finish_reason = "length"`, 1424; 1457 in 0.32.0), so it produced a
   one-token completion rather than an error. The server calls
   `insert_segments` at 742–745 (`max_tokens=[args.max_tokens]`) in the body of
   `_generate`'s `while not self._stop:` loop, with no `try` around it. The
   `try/except Exception` that turns a failure into `rqueue.put(e)` guards the
   tokenisation (706–709) and the model load (772–777), not the insert.
3. **The exception ends the thread.** It propagates out of `_generate` into the
   new wrapper (446–451):

   ```
   def _run_generate(self):
       try:
           self._generate()
       except Exception as e:
           logging.exception(f"mlx_lm.server generation thread died: {e}")
           self._generation_failed = True
   ```

   In 0.31.3 the thread was `Thread(target=self._generate)` and the same
   exception killed it silently. What 0.32.0 adds is that the death is now
   visible: `generation_available()` (453–454) is false, `generate()` raises
   `RuntimeError("generation thread died")` for every later request (1029–1030),
   a request already waiting gives up within a second (`_await_response`,
   1012–1020), and `/health` answers `503` with `{"status": "unavailable"}`
   (`handle_health_check`, 1651–1662). The process and its listener stay up.
4. **Who can send it.** Any client that reaches the gateway. A request with
   `"max_tokens": 0` or `"max_completion_tokens": 0` (or `false`) on a batchable
   model reaches the server unaltered: the gateway's `requestedMaxTokens` reads
   a zero as "asked for nothing in particular" and relays it, and nothing in
   `internal/gateway` refuses a non-positive budget. After one such request the
   model answers every completion with a `404` carrying `{"error": "generation
   thread died"}` until it is restarted, and the pool does not poll `/health`,
   so Dessau keeps counting it as ready. The same value as an operator's saved
   default does the same on every request that omits a budget, because
   `config.SamplingBound` for `max_tokens` has `Min: 0` and `samplingArgs`
   passes a `0` through (`launchSampling` keeps an operator budget that
   `Sanitized` accepts).
5. **The single-request path** (a request with `seed`, a model whose cache is
   not batchable, a draft model, or `--kv-bits`) changed too, more gently.
   `stream_generate` now begins with

   ```
   if max_tokens == 0:
       raise ValueError(
           "Maximum number of tokens must be non-zero (use -1 for no limit)."
   ```

   (`generate.py` 687–690). `_serve_single` catches it (1009–1010) and hands it
   to the request thread, which raises it uncaught out of `handle_completion`:
   that one connection closes with no response, the gateway answers `502`, and
   the thread survives.

**Dessau needs to change**, in this order of importance:

- Refuse a zero (and `false`) `max_tokens` / `max_completion_tokens` at the
  gateway with a `400` naming the field, before the model is resolved, on the
  same relay paths as the `draft_model` / `adapters` refusal. Any value the
  server's own check accepts and its batch insert refuses is the set to refuse:
  integer `0` (including `-0`) and `false`. Negative and float values already
  fail the server's request check without killing anything.
- Raise the lower bound of `max_tokens` in `config.SamplingBound` from `0` to
  `1`, so neither the settings endpoint nor a hand-edited `config.json` can
  produce `--max-tokens 0`. Per the repository's rule a hand-edited
  out-of-range value is dropped with a start-up warning, not a refused file.
  `TestGoRangesAreExactlyThese` and
  `TestGoRangesAreNeverWiderThanThePinnedServers` pin the table and will say so;
  the reference page and the panel's placeholder follow.
- Consider treating a `503` from the child's `/health` as a crashed model so
  the pool restarts it. It is not needed for the fix above, but it is the only
  signal the server now gives that its generation thread is gone, and a thread
  can die for reasons other than this one.

## 3. `model_file` and the other ways a model directory runs code: HOLDS

**The trigger is the same key.** `load_model` in `mlx_lm/utils.py` still
begins its branch on the config's `model_file` (457):

```
if (model_file := config.get("model_file")) is not None:
```

and, where the file is allowed, still builds it with `spec_from_file_location`
and `exec_module` and takes `arch.Model, arch.ModelArgs` (465–471). The test is
`is not None`, so an empty string and any non-null value still count, which is
the condition `registry.CheckModelCode` copies.

**Tighter than 0.31.3, not looser.** The server now declines by itself unless
asked to trust the code. `load_model` and `load` gained a
`trust_remote_code: bool = False` parameter (`utils.py` 414 and 618), and the
branch begins (458–464):

```
if not trust_remote_code:
    raise ValueError(
        f"The model at {model_path} requires importing and running a "
        f"custom module ({model_file!r}) to build its architecture. This "
        "is disabled by default. Pass trust_remote_code=True if you "
        "trust this model."
```

The server passes `trust_remote_code=self.cli_args.trust_remote_code` (339 and 346), and `--trust-remote-code` is a `store_true` flag
(1816–1818). `serve.py` refuses a launch that sets it, so in Dessau the value is
always `False` and a `model_file` model now fails at load with this message even
if Dessau's own refusal were bypassed. Dessau's refusal stays correct and stays
first, since it names the reason and acts before a process is spent. The draft
loader gets the same protection by default: `load(draft_model_path)` (357) takes
`trust_remote_code=False`. Nothing is required of Dessau. The wording of the two
refusals differs, which matters only to a test that matches the child's message,
and none does.

**Other ways a model directory can make the server import code.** Nothing new
in `mlx_lm`; the four routes that exist were already there.

| Route | 0.32.0 | Verdict |
| --- | --- | --- |
| `auto_map` in `tokenizer_config.json` (custom tokenizer class) | `AutoTokenizer.from_pretrained(model_path, **(tokenizer_config_extra or {}))`, `tokenizer_utils.py` 698–700. The server's tokenizer config is now `{"trust_remote_code": cli_args.trust_remote_code}` (306), that is `False`; it was `True if cli_args.trust_remote_code else None`. In `transformers` 5.14.1, `resolve_trust_remote_code` with `None` and a repository carrying remote code opens an interactive `input()` prompt under a `SIGALRM` timeout, which a child without a terminal turns into a `ValueError` (`dynamic_module_utils.py` 755–779); with `False` it reaches the plain refusal at 787–791 at once. Either way the code is not run. | HOLDS, and no longer depends on the child having no stdin. |
| `chat_template_type` in the tokenizer config | `importlib.import_module(f"mlx_lm.chat_templates.{chat_template_type}")`, `tokenizer_utils.py` 704–707. Imports only a submodule of the shipped package; a model cannot name its own file. | HOLDS (identical to 0.31.3, line 620). |
| `tool_parser_type` in the tokenizer config | `importlib.import_module(f"mlx_lm.tool_parsers.{tool_parser_type}")`, 713–714; inferred from the template text when absent (710–711). Same restriction. The parsers use `ast.literal_eval`, never `eval` or `exec`. | HOLDS. |
| `model_type` / `architectures` in `config.json` | `importlib.import_module(f"mlx_lm.models.{model_type}")`, `utils.py` 221. The new `MODEL_ARCHITECTURE_REMAPPING` (62–66, used at 210–219) maps a `(model_type, architecture)` pair to a fixed module name from a table in the source. | HOLDS. |
| Chat-template text (`chat_template` in the tokenizer config, a `.jinja` file) | Rendered by `transformers`, whose `apply_chat_template` uses an `ImmutableSandboxedEnvironment` (`chat_template_utils.py` 489). Not `mlx_lm` code; the same `transformers` pin. | HOLDS (outside this bump). |

Not new, and not reachable: `server.py` imports `pickle` and calls
`pickle.loads` (508) in `_share_object`, which runs only when
`mx.distributed.init()` reports a group larger than one; a Dessau child is a
single process. `--chat-template` and `--chat-template-args` take their value
from the command line, which Dessau does not pass.

## 4. Refused request fields: HOLDS

Both fields are still read from the request body, unvalidated as to location,
and still handed to the loader. In `do_POST`:

```
self.requested_draft_model = self.body.get("draft_model", "default_model")   # 1162
...
self.adapter = self.body.get("adapters", None)                               # 1166
```

`draft_model` has no type check; `adapters` is checked only as an optional
string (`self._validate("adapter", str, optional=True)`, 1247). Both go into
`ModelDescription(model=..., draft=..., adapter=...)` and from there to
`self.model_provider.load(args.model.model, args.model.adapter, args.model.draft)`
(772–774). `ModelProvider.load` (381–390) maps `"default_model"` through the
launch-time maps and passes anything else through as a path, then `_load`
loads a draft with `load(draft_model_path)` (357) and an adapter with
`load(..., adapter_path=adapter_path, ...)` (343–347), which calls
`load_adapters` and reads `adapter_config.json` and `adapters.safetensors` from
that path. `load_adapters` now checks the tensors against the model's
parameter shapes before applying them (`tuner/utils.py` 147–170) and passes
the weights to `model.load_weights`, but the path is still the client's. A
model whose directory carries `model_file` is no longer executed from either
path without `trust_remote_code` (check 3), which narrows what the draft path
can do and does not change the reason for refusing it.

`serve.py` refuses by the key's presence, so its `REFUSED_FIELDS` remain exact:
the server reads `draft_model` and `adapters` with `body.get(...)`, which treats
an explicit `null` as present-with-no-value, and the launcher refuses the key
whatever its value.

**No new request field names anything to load.** The set of keys the handler
reads from the body is identical to 0.31.3's: `adapters`, `chat_template_kwargs`,
`draft_model`, `frequency_context_size`, `frequency_penalty`, `logit_bias`,
`logprobs`, `max_completion_tokens`, `max_tokens`, `min_p`, `model`,
`num_draft_tokens`, `presence_context_size`, `presence_penalty`,
`repetition_context_size`, `repetition_penalty`, `role_mapping`, `seed`,
`stop`, `stream`, `stream_options`, `temperature`, `tools`, `top_k`,
`top_logprobs`, `top_p`, `xtc_probability`, `xtc_threshold`, plus `messages`
and `prompt`. `model` is still the only other field that selects a path, and
`serve.py` overwrites it. `ModelProvider.load` does reorder its two map
lookups (the model map is now consulted after the adapter map, 382–383), but
because `serve.py` sends the real model path rather than `"default_model"` the
lookups find nothing in either order, and the launcher refuses a launch that
names an adapter or a draft model.

What is different around those names, and does not touch them:

- `run()` in `mlx_lm` is unchanged in shape: it initialises
  `mx.distributed`, builds the prompt cache and the `ResponseGenerator`, then
  calls `_run_http_server` on rank 0 (1764–1770). The launcher replaces all of
  it, as it replaced the 0.31.3 version, and `ResponseGenerator.__init__` still
  initialises `mx.distributed` itself (440).
- `ResponseGenerator.__init__` now starts `Thread(target=self._run_generate)`
  (443–444), which calls `self.model_provider.load_default()` first thing
  (662). That is the same point at which the model loads in 0.31.3, so the
  readiness probe's reading of a load failure is unchanged.
- At the end of `_generate` the thread now resets the provider and deletes the
  prompt cache (899–900: `self.model_provider.reset()`,
  `del self.prompt_cache`). That runs after `stop_and_join()` has set `_stop`
  and joined, so `serve.py`'s `KeyboardInterrupt` path is unaffected.
- `main()` now calls `maybe_set_recommended_wired_limit()` (1931) in place of
  the explicit `mx.set_wired_limit`, and passes `ModelProvider(args)` to `run`
  as before.
- The `/health` handler is the one the pool does not poll (check 2).

`serve.py` needs no edit. The `Requires-Python` of the wheel moves to `>=3.11`;
the runtime is provisioned at 3.12 (`pythonVersion` in `provision.go`), so that
holds too.

## 6. DEBUG logging: HOLDS

What the server writes at DEBUG is the same, call site for call site; only the
line numbers move.

| Call | 0.31.3 note | 0.32.0 |
| --- | --- | --- |
| `logging.debug(f"Incoming Request Body: {debug_body}")`, guarded by `isEnabledFor(logging.DEBUG)` | 1147–1149 | 1145–1147 |
| `logging.debug(gen.text)` | 1456 | 1460 |
| `logging.debug(f"Outgoing Response: {response_debug}")`, same guard | 1542–1544 | 1560–1562 |
| `logging.debug("Starting stream:")` / `("Starting completion:")` | 1434 / 1437 | 1435 / 1438 |
| `logging.error(f"JSONDecodeError: {e} - Raw body: {raw_body.decode()}")` | 1139 | 1137 |
| `logging.error(f"Invalid Request Body: {debug_body}")` | 1152 | 1150 |
| `logging.basicConfig(level=..., format=...)` | 1892 | 1933–1936 |
| `--log-level`, `default="INFO"`, `choices=[...]` | 1798–1804 | 1821–1827 |

So at DEBUG the server still writes the whole request body, every generation
step's text, and (non-streaming only) the whole response; there is still no
file handler, no size bound and no redaction; and the two content lines that
are written at ERROR today, for a body that is not JSON and one that is not an
object, are still written at the default level. The streaming branch still has
no `Outgoing Response` line of its own. `launchArgs`'s `"--log-level", "INFO"`
is still accepted by the parser.

Two differences of detail, neither of which changes a decision:

- **One new line, at ERROR, in `_run_generate`:** `logging.exception(f"mlx_lm.server
  generation thread died: {e}")` (450), which writes the exception text and a
  traceback. It is written at the default level. The text is whatever the
  failing call raised; for the zero-budget case in check 2 that is a fixed
  string, but a tokeniser or template error can carry fragments of the request.
  It is in the same class as the two existing ERROR lines, and the per-model
  log's size bound at DEBUG is the only bound it has.
- `logging.debug(gen.text)` logs one step's text as before, but in the batched
  path the stop token is no longer decoded (`# Don't decode the final stop
  token`, 850), so the last step's text is empty rather than the stop token's.
  The 0.31.3 sentence that the answer is on disk either way is unchanged.

## 7. Streaming usage: HOLDS

The final usage chunk is produced exactly as in 0.31.3. In
`handle_completion` (1534–1545):

```
if (
    self.stream_options is not None
    and self.stream_options["include_usage"]
):
    resp = self.completion_usage_response(
        len(ctx.prompt),
        len(tokens),
        ctx.prompt_cache_count,
    )
```

`stream_options` is read at 1160; the chunk is built by
`completion_usage_response` (1572–1593), `"choices": []` and a `usage` object
of `prompt_tokens`, `completion_tokens` and `total_tokens`, with
`prompt_tokens_details.cached_tokens` added when the cache count is not
negative. `prompt_tokens` is `len(ctx.prompt)` and `completion_tokens` is
`len(tokens)`, where `tokens` collects every step's token including the one
that finished the reply (`tokens.append(gen.token)`), so the count is the
same as before. The key is still read with `[]`, so a `stream_options` object
without `include_usage` still raises part-way through the answer, as the
comment in `assemble.go` says, and `askForStream` replacing the client's
object remains right. `readUsage` in the gateway reads `prompt_tokens` and
`completion_tokens` off the event, and both names are unchanged.

One response-shape change that does not touch usage: a non-streamed chat reply
with no text now carries `"content": null` rather than omitting the key
(`choice[key_name]["content"] = text if text else None`, 1354–1355, with the
comment "The schema requires "content" field to be present"). Streamed chunks
still omit it when empty (`elif text:`, 1356). The gateway does not read
`content` of a non-streamed answer, and `internal/gateway/assemble.go` builds
its own message from streamed deltas, so nothing is required of Dessau; the
change is recorded because a test that pins the server's empty-reply shape
would see it.

## 8. Telemetry and network: HOLDS

There is no telemetry in 0.32.0's server path. A search of the whole package
for `opentelemetry`, `otel`, `telemetry`, `sentry`, `analytics`, `posthog`,
`mixpanel`, `wandb`, `requests`, `urllib`, `http.client`, `aiohttp`, `httpx`
and `webbrowser` finds nothing, in either version. The new module
`generate_utils.py` is local counters (`BatchCounters`, `BatchStats`: token
counts and elapsed time) with no I/O.

The network-capable calls are the ones 0.31.3 had, unchanged in behaviour:

- `snapshot_download` in `_download` (`utils.py` 285–290), reached only when
  the model path does not exist locally. Dessau passes an existing directory,
  and the child runs with `HF_HUB_OFFLINE=1`. Its allow-pattern list was
  hoisted into `DEFAULT_ALLOW_PATTERNS` (251–261), unchanged in content.
- `hf_repo_to_path` (`utils.py` 300), now with the same patterns, and
  `local_files_only=True`.
- `scan_cache_dir()` in the `/v1/models` handler, which reads the local cache
  and is not routed by the gateway.
- `socket.getaddrinfo` in `_run_http_server`, which `serve.py` bypasses.

**New environment variable: `MLX_GDN_PACKED`** (`models/gated_delta.py` 15:
`_ENABLE_GDN_PACKED = os.environ.get("MLX_GDN_PACKED", "1") != "0"`). It is read
when a gated-delta model module is imported and only selects between two
compute kernels; it has no network or file effect. Two environment variables
that were already there stay: `TRANSFORMERS_NO_ADVISORY_WARNINGS` is set by
`mlx_lm/__init__.py`, and `MLXLM_USE_MODELSCOPE` (`utils.py` 29) switches model
download to ModelScope when it is `"true"`. Neither is new, and the second is
worth one sentence: `-I` ignores `PYTHON*` variables only, and the launcher
builds the child's environment from `os.Environ()`, so a variable set in the
serving account's environment reaches the child. That is the same exposure as
under 0.31.3, and it does not matter while the model path is a local directory.

## What else moves with the bump

- **Dependency floor.** The 0.32.0 wheel's metadata requires
  `mlx>=0.32.2` (0.31.3: `>=0.31.2`), `transformers>=5.7.0` (`>=5.0.0`) and
  Python 3.11 or later. The lock this note was written against pinned
  `mlx==0.32.0` and `mlx-metal==0.32.0`, below the new floor; the lock
  regenerated with the bump pins both at 0.32.3, the signed-off figure; the
  `transformers==5.14.1` and Python 3.12 pins already satisfy the new floors.
- **Constants and tests to move together:** `mlxLMVersion` in `provision.go`,
  `samplingFlagsVerifiedAgainst` in `launcher.go`, the version mentioned in
  `serve.py`'s comments and in the 2026-10-03 DECISIONS lines (those lines are
  append-only and stand; a new dated line supersedes where needed), and the
  `max_tokens` bound in `config.SamplingBound` with the tests that pin it.
- **A hand check owed on macOS** before the pin lands: with a small batchable
  model, send `{"max_tokens": 0}` twice and confirm the second answer is the
  `404` `generation thread died`, and that `GET /health` on the child's socket
  answers `503`. If it does not, the static trace in check 2 is wrong and the
  gateway refusal is still harmless.
