# What the pinned model server writes at DEBUG in mlx-lm 0.31.3 — 2026-09-20

The pinned model server is `mlx-lm==0.31.3`
(`internal/runtime/mlx-requirements.txt` line 211; `mlxLMVersion` in
`internal/runtime/provision.go` line 50). This note records what that exact
version writes at its `--log-level DEBUG`, and what bounds it. It is the
precondition finding 1 of the 2026-09-19 review of itd-2609062346072707
names: the earlier note that carried this claim read the project's main
branch and said in as many words to verify it against the pin before relying
on it.

Method: the pinned wheel is fetched from PyPI with `pip3 download
mlx-lm==0.31.3 --no-deps`, unzipped outside the repository, and
`mlx_lm/server.py` is read directly — its `main()` argument parser, its
`do_POST` body handler, and the generation loop in `handle_completion`.
Line numbers below are that file in that wheel (1,904 lines;
`mlx_lm/_version.py` reports `0.31.3`). Nothing here is inferred from
documentation or from another version. There is no provisioned runtime on the
machine this was read on — the account's application-support folder for the
app is empty — so the wheel, which is the artefact provisioning installs, is
the source and there is no installed copy to differ from.

## Verdict: both bodies, in full

At DEBUG the server writes **(a) the full request body, including the whole
`messages` array, and (b) the full generated response** — not metadata only.
Three call sites carry the content:

| Where | Call | What it writes |
| --- | --- | --- |
| line 1147–1149 | `logging.debug(f"Incoming Request Body: {debug_body}")`, guarded by `logging.getLogger().isEnabledFor(logging.DEBUG)` | the parsed request body re-serialised with `json.dumps(self.body, indent="\t")` — every message, the system message, the tools, the parameters |
| line 1456 | `logging.debug(gen.text)` | every generation step's text, one line per step, for streaming and non-streaming alike |
| line 1542–1544 | `logging.debug(f"Outgoing Response: {response_debug}")`, under the same `isEnabledFor` guard | the complete non-streaming response object, `json.dumps(resp, indent="\t")` — the completion text, and the tokens and logprobs where the request asked for them |

Two further DEBUG lines are metadata only: `logging.debug("Starting stream:")`
and `logging.debug("Starting completion:")` (lines 1434 and 1437).

A streaming request is logged too, by line 1456: the per-step text arrives
token by token rather than as one object, so the answer is on disk either
way. The streaming branch (lines 1507–1528) has no `Outgoing Response` line
of its own.

One content line is written at a level below DEBUG and so is written today:
`logging.error(f"JSONDecodeError: {e} - Raw body: {raw_body.decode()}")`
(line 1139) puts an unparseable body in the log at ERROR, and line 1152 does
the same for a body that parses but is not a JSON object. That is a request
that never reached a model, not a prompt a model answered, but it is content
from the network and it is already reaching the per-model log at INFO.

## No size bound of any kind

The level is set once, at start-up, by `logging.basicConfig(level=...)`
(line 1892) from the `--log-level` flag (lines 1798–1804: `default="INFO"`,
`choices=["DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"]`). That is the
only level switch: a running process has no way to change it.

`basicConfig` is the whole of the logging configuration. The file installs no
`FileHandler`, no `RotatingFileHandler` and no `maxBytes` — the only match for
any of them in `mlx_lm/server.py` is that one `basicConfig` call. Nothing
truncates, samples, rate-limits or redacts either body: `debug_body` and
`response_debug` are `json.dumps` of the whole object, with `indent="\t"`,
which makes them larger than the wire form rather than smaller.

So the bound is Gropius's to add. Records go to the default stream handler,
which the launcher points at the per-model file
(`internal/runtime/launcher.go` lines 303–304 assign the same handle to
`cmd.Stdout` and `cmd.Stderr`), opened `O_TRUNC` at 0600 (line 292). Today
that truncation at the next launch is the only thing bounding those logs, and
`docs/logging.md` says so. At DEBUG a client that loops writes bytes of its
own choosing into that file for as long as the model stays up.

## What this settles for the record

Shape (i) of itd-2609062346072707 Question 2 — raise the child's level rather
than have the gateway write the log — is available at the pin, and delivers
what the intent asks for: the request body is exactly "what the client is
actually sending", and the answer is there beside it. The maintainer's
2026-09-20 answer was conditional on this verification, and the condition is
met, so it stands.

Two of its costs are confirmed rather than feared. The content is unredacted
and complete, so an API key a client puts in a message is written verbatim.
And it is unbounded, so the size bound the same answer asks for is Gropius's
own work at the file, not a flag the server offers.

The launcher's `"--log-level", "INFO"` (line 235) is what holds all of this
off today, and `TestTheModelServerIsAlwaysLaunchedAtInfo`
(`internal/archtest/statistics_switch_test.go` line 97) is what holds the
launcher there.
